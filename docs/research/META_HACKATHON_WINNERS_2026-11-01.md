# Meta AI hackathon winners: evidence and lessons for Glint

Research date: November 1, 2026 (America/New_York).

This is a verified research set of **31 winners, category awardees and explicitly
named runners-up across eight relevant Meta-associated AI hackathons**. It is not
a claim to list every Meta hackathon worldwide. Competitive-programming Hacker
Cup, Horizon/Quest game competitions, grants and startup accelerators are excluded
because their objectives differ from Glint's AI-app submission. Unverified same-name
GitHub projects are not substituted for missing winner repositories.

Award facts come from Meta, event organizers or event partners. Repository
observations come from current public READMEs and repository layouts; these may
have evolved since judging. No downloaded project was executed. Except where an
organizer explains a strength explicitly, the pattern analysis below is an
inference, not a judge's scorecard or a proven explanation of why a team won.

## What inspecting the repositories actually shows

| Repository | Observed evidence | Useful lesson for Glint |
|---|---|---|
| [OpenGlass](https://github.com/BasedHardware/OpenGlass) | Hardware setup, Expo/local run instructions, video; project later moved to Omi | A memorable physical interaction can carry a demo. Do not equate a website deployment with a complete product experience. |
| [OrgLens](https://github.com/TheCl3m/llama-hack) | Django + React/Vite; GitHub-derived context; PlayAI/Groq voice; local setup and embedded demo | Ground the assistant in task evidence. A separate speech provider is compatible with substantive Meta model usage. |
| [Compliance Wizards](https://github.com/michaelwaves/llamacon-hackathon) | Frontend/backend directories, sparse README mostly containing API/GPU notes | Award status does not prove documentation quality or production readiness. Do not copy its rough edges. |
| [CCTV Operator](https://github.com/torayeff/llamacon-hackathon-2025-sf) | Chunker → detector → event queue → database; user-defined events; UI walkthrough | Bound the visual task and show detected evidence. Decoupling capture and analysis is useful when the product needs it. |
| [geo-lm](https://github.com/williamjsdavis/geo-lm) | Explicitly a prototype; document → geology DSL → GemPy; local UI/API and tests | Convert model understanding into a domain artifact that users can inspect, rather than adding another generic chat screen. |
| [GripMind](https://github.com/gabrycina/llama-lerobot) | Vision/robotics/EEG integration; smaller-model/offline deployment still listed as roadmap | A focused working demonstration can coexist with unfinished production ambitions. Distinguish implemented from planned. |
| [AcuteReport](https://github.com/martinjnilsen/acutereport.ai) | React/Vite, FastAPI, local Llama 3.3/vLLM, MongoDB and Docker Compose | A domain workflow with reproducible deployment instructions is more informative than a hosting badge. |
| [SafeScreen candidate](https://github.com/doctarpolmz/safescreen-ai) | Measured CPU path, pending NPU work and explicit model limitations, despite broader headline wording | Use the detailed status/limitations over marketing claims; do not reproduce an unsupported performance claim. |
| [Toddle AI](https://github.com/preyashyadav/toddle-ai) | Capture-quality gate, deterministic measurements, grounded explanation; distinguishes installed app from NPU experiments | Asking for better evidence and withholding an unsupported result can be a product strength. |

Repository coverage: eight strong award/team-to-repository matches, plus two
explicitly labeled candidates (SafeScreen and CurePharma). The Evalssment name
also appears in a repository now describing a different tutoring product; it is
not presented as verified code for the grading project that won in 2024.

These observations establish local/prototype workflows in the present repository
documentation. They do **not** establish whether a team had an additional hosted
deployment at submission time. GitHub stars, current commit counts and later
commercial success were not used as explanations of judging outcomes.

## Patterns, with the confidence they deserve

1. **Specific users and a concrete task.** Finding an internal expert, detecting a
   declared CCTV event or explaining a child's usable walking clip is easier to
   assess than an assistant claiming to do everything. This is a recurring trait,
   not proof that every broad project loses.
2. **Capabilities matter when they change the workflow.** Visual understanding,
   long context, language access and local inference have a product reason. The
   number of APIs or models integrated is not, by itself, evidence of value.
3. **A visible result helps.** An event alert, 3D model, robotic action or improved
   speaking feedback gives a judge something observable. Technical infrastructure
   matters insofar as it makes that result work reliably.
4. **The right delivery surface varies.** Local mobile apps, hardware, WhatsApp and
   localhost web demos all appear in this set. Paid public hosting is not the
   common denominator. Reproducibility and an accessible demonstration still matter.
5. **Domain detail and accessibility are recurring strengths.** Local language,
   constrained connectivity, specialist context and capture quality can make an
   otherwise familiar AI capability useful to a specific person.
6. **Acknowledge the boundary of the evidence.** The 2026 edge recap explicitly
   commends privacy and explainability; Toddle's repository describes quality
   rejection. This supports presenting uncertainty honestly, not pretending every
   camera frame produces a reliable answer.

Most historical sources announce ranks and describe products without publishing
numeric judge scores. We cannot recover the exact causal reason for each win,
compare every winner to every losing entry, or estimate Glint's probability of
winning from this sample. The current rubric is stronger guidance than speculative
claims that a feature, model count, hosting vendor or presentation trick guarantees
a prize.

## Recommendation for Glint before paying for production

My recommendation is to prioritize a reliable, task-focused submission package,
especially if Glint is entered in the indie track. This is advice based on the
evidence above, not a statement that production is forbidden or never valuable.

Suggested positioning: **Glint helps a beginner complete a hands-busy real-world
task through a camera-grounded conversation, with visual explanations when useful.**
Avoid making “an assistant that sees and talks” the entire novelty claim: OpenGlass,
Pitch Perfect, AthletIQ and other winners already occupy related territory.

Suggested priority order:

1. Inspect the signed-in submission form and organizer FAQ for the actual required
   artifacts, video length, repository access and deployed-URL rules.
2. Pick one hero scenario from observed use, such as beginner cooking assistance.
   Show a clear question, evidence from the camera, a useful next step and the
   user's follow-up. Avoid adding a new domain just for a prize narrative.
3. Make one continuous demonstration robust: camera question → useful response →
   interruption → resumed or corrected conversation → finished task interaction.
   Include one poor-view example where Glint asks for a better frame.
4. Show each Meta model's actual role. Spark reasons over task/camera context;
   Image creates an explicitly requested illustration; SAM analyzes requested
   object evidence where that feature genuinely helps. Do not insert all models
   into every workflow to inflate an integration count.
5. Record a clean demo video and provide reproducible setup, required keys,
   tested environment, architecture diagram, limitations and a sample walkthrough.
   Explain cloud image edits as generated illustrations, not observed proof.
6. Use measured product evidence: task completion, answer usefulness, recovery
   behavior and end-to-end response times. Passing hundreds of tests is engineering
   evidence, not a substitute for showing user value.
7. Add permanent hosting if the actual rules require it, judges need independent
   access, or it is inexpensive to finish without compromising the demonstration.
   A temporary live demo also requires the laptop/tunnel to stay available. Never
   promise judges a link that will be offline when they try it.
